Truly static matters

November 18, 2025 (1 day ago) @boborgo

The problem with dynamic static sites

When I first built Ez Blog, I thought I had created a static blog. After all, it was just HTML, CSS, and vanilla JavaScript—no server-side rendering, no database, no backend. It worked perfectly on GitHub Pages.

But I was wrong. While the files were static, the content wasn't. Each post page was essentially a template that relied on JavaScript to fetch and inject the HTML content at runtime. The homepage dynamically loaded post metadata from a JSON file. This meant that:

  • Search engine crawlers had to execute JavaScript to see the content
  • Social media platforms (LinkedIn, Twitter, Facebook) couldn't generate proper preview cards
  • The initial page load showed empty templates before JavaScript kicked in
  • SEO was suboptimal because crawlers might not wait for JavaScript execution

I realized I had built a "dynamic static site"—a contradiction that was hurting discoverability and sharing.

Why truly static matters

If a tree falls in a forest and no one is around to hear it, does it make a sound? If a blog post exists but crawlers can't index it, does it matter?

For a personal blog, discoverability is crucial. I wanted people to find my content through search engines and share it on social platforms. The dynamic approach was creating barriers:

Social media sharing

When you share a link on LinkedIn, Twitter, or Facebook, these platforms send a crawler to fetch metadata (title, description, image) for the preview card. These crawlers are fast and efficient, but they don't execute JavaScript. They look for meta tags in the raw HTML.

With my dynamic approach, the crawler would see an empty template with generic meta tags, not the post-specific information. The result? Ugly, generic preview cards that didn't represent the content.

Performance and reliability

Truly static sites are faster. There's no JavaScript execution delay, no network requests to fetch content, no risk of JavaScript errors breaking the page. The content is just there, ready to be served immediately.

The solution: Ez Blog 2.0

I rebuilt the blog as Ez Blog 2.0, a static site generator that pre-renders everything during the build process. Now, instead of templates that load content dynamically, the build script generates complete HTML pages for each post.

How it works

The build process is straightforward:

  1. Read post metadata from DB_posts.js
  2. Load HTML content from individual post files
  3. Generate complete HTML pages with proper meta tags, Open Graph tags, and Twitter Cards
  4. Generate the homepage with all posts pre-rendered
  5. Generate SEO files like robots.txt and sitemap.xml

I keep my drafts in a separate directory that's versioned in a private repository. A symlink connects this directory to the main blog project, allowing the build script to access the draft files without exposing them in the public repository. When I run the build, it reads from the linked drafts directory and generates the final posts in the posts/ directory. Only these generated files are published—the drafts remain private.

Each generated post page is a complete, self-contained HTML file with:

  • Proper meta tags for SEO
  • Open Graph tags for Facebook and LinkedIn
  • Twitter Card tags for Twitter
  • Structured data (Schema.org) for rich snippets
  • All content embedded directly in the HTML

The build system

The build system is a simple Node.js script that:

  • Reads the configuration from build.config.json
  • Processes each post and generates a complete HTML page
  • Copies assets (images) to the output directory
  • Generates the homepage with all posts
  • Creates robots.txt and sitemap.xml automatically

Running node build.js transforms your drafts into a fully static website ready for deployment.

The results

After migrating to Ez Blog 2.0, the improvements were immediate:

  • Better SEO: Search engines can index content immediately without executing JavaScript
  • Perfect social sharing: LinkedIn, Twitter, and Facebook now show proper preview cards with titles, descriptions, and images
  • Faster load times: No JavaScript execution needed to display content
  • Better reliability: No risk of JavaScript errors preventing content from loading
  • Improved accessibility: Content is available even if JavaScript is disabled

Lessons learned

This migration taught me an important lesson: static doesn't just mean "no server-side code." It means the content is fully rendered and ready to serve, without requiring any client-side processing.

For a blog hosted on GitHub Pages, truly static is the way to go. It's simpler, faster, more reliable, and works better with search engines and social media platforms. The build step adds a small amount of complexity to the workflow, but the benefits far outweigh the costs.

If you're building a blog or documentation site, consider using a static site generator. Your future self (and your readers) will thank you.
