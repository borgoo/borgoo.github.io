Why? (-have I started)

Because I can.

In the last year I started coding on platforms like LeetCode and testing myself with challenges like Advent of Code. The goal was to sharpen my coding and problem-solving skills.

During this journey, I began reflecting on how much knowledge I was accumulating and how easily it could be forgotten in a few years.

I'm the kind of person who loses skills I don't use daily, yet I've often found myself needing to re-learn things I already knew. Having a centralized place to document my learning process seemed like it could help future-me (and maybe others too).

Plus, the different platforms I use for practice don't really support this concept of knowledge centralization.

So... here I am.

What started as a styling exercise evolved into something practical: a way to improve my English through writing while sharing my thought processes and learnings with other developers.

How? (-this is done)

I began by developing a static blog system using HTML, CSS and pure JavaScript: Ez Blog

These technologies are easy to maintain and deploy seamlessly on GitHub Pages.

With that foundation set, I needed to figure out how to fake some dynamism for the content. The approach I settled on was straightforward:

  • Create a database of posts
  • Create a page for each post
  • Create a homepage that lists all posts

Create a database of posts

Since I don't expect heavy traffic or complex performance requirements, and because GitHub Pages is my target platform, a simple JSON file made perfect sense for storing post metadata.

Almost immediately, I realized that a massive JSON file containing all posts' HTML content would be nightmarishly inelegant (imagine this file with all that HTML wrapped in backticks ☠️).

The solution was obvious: externalize the HTML content. Each post's content lives in its own file, while the JSON database only stores lightweight metadata.

After implementing this separation, I wrote the logic to bind the HTML content files with the JSON metadata using a contentFile field. Much cleaner.

For the post identifier, I chose URI-compatible titles rather than array indices. This avoids two critical problems:

  1. Fragility—inserting posts anywhere but the end would break the indexing
  2. Future-proofing—if I ever implement server-side sorting or pagination, old links won't break

Finally, I implemented the JavaScript logic (post.js) to fetch and inject the HTML content into a common post template (post.html).

Create a page for each post

By the time I got here, I'd already solved this problem: each post is simply the combination of its metadata and HTML content, rendered through the shared template.

Create a homepage that lists all posts

This turned out to be the easiest part—just some JavaScript logic (main.js) to load and display the post metadata from the JSON database.
